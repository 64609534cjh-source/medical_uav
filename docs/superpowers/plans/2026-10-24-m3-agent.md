# M3 Learning Agent Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the scratch-PPO results into a credible M3 learning agent: traceable runs, rule-based checkpoint selection, an audited visible-order rollout planner, the reward and imitation controls, behaviour analysis, and an M3 package with a selected trained model.

**Architecture:** Builds on branch `m3-ppo`. Reward variants are environment settings; the planner is a baseline in `medical_uav/baselines/rollout.py`; selection and analysis are scripts over checkpoints in `runs/`. The selected model is copied to `checkpoints/ppo_set.pt` for the submission.

**Tech Stack:** Python 3.11.17, PyTorch 2.14.1 (CPU), NumPy, Gymnasium, pytest.

**Spec:** `docs/superpowers/specs/2026-10-23-roadmap-to-final.md` (§3 environment, §4 seeds and selection rule, §5 agents, §6 baselines, §7 milestones, §9 evidence); Codex audit 2026-10-24 (priorities 2–6) in `docs/superpowers/experiments/2026-10-24-m3/codex_audit.md`.

## Global Constraints

- Branch `m3-ppo`; nothing merged into `main` (owner); push only with approval. Commit messages have no co-author trailer.
- Lean, readable code; TDD for every code change; long runs only after their code passes tests.
- Seeds: screen 100000–100039, select 100040–100139, test 200000–200299 (untouched), demonstrations 0–999, online RL 1000–99999, training seeds 11, 22, 33 (controls) plus 44, 55 (primary agent).
- Selection rule (roadmap §4): one checkpoint per run, the same for all loads; eligible if low-load on-time ≥ 0.97 and, at medium and high load, every order type's pooled on-time rate is at most 3 points below Slack-aware's on the same days; among eligible checkpoints the highest mean of medium and high on-time rate wins; ties go to the earlier checkpoint. If none is eligible, report it.
- PPO settings unchanged from Part C of the M2 plan; budget 6 M decisions per run; all variants keep the network, observation, dynamics and PPO settings fixed.
- Every run and result file records the environment version, reward variant, git revision and seeds.
- Claims: screen/select/test kept apart; no "optimal", "upper bound" or "state of the art" without evidence.

## Review Focus

- A run directory whose checkpoint names repeat another run's (selection must key by path) (Task 3).
- The planner must not change its choice when hidden or future orders change (Task 4).
- BC → PPO warm-up must leave the policy's action probabilities unchanged (Task 5).
- The M1 reward variant must reproduce the M1 reward exactly, including the linear late reward (Task 2).
- A checkpoint that is never eligible must be reported, not silently replaced (Task 3).

### Task 3: Checkpoint selection

**Files:** Create `scripts/select_checkpoints.py`; Modify `medical_uav/evaluation.py`; Test `tests/test_evaluate.py`

**Interfaces:**
- Consumes: `run_day`, `SELECT_SEEDS`, `load_checkpoint`, `NetworkPolicy`.
- Produces: `select_checkpoint(results: dict[str, dict], slack: dict) -> tuple[str | None, list[dict]]` in `medical_uav/evaluation.py`: `results` maps a checkpoint path to `{load: {"on_time_rate": float, "on_time_<type>": pooled rate}}`; returns the chosen path (or `None`) and one row per checkpoint with `eligible`, `reason`, `score`. CLI `python scripts/select_checkpoints.py runs/m3_set_s11 runs/... --processes 18 --out runs/selection.json`: evaluates every checkpoint of every run on the 100 selection days at all loads (in parallel), plus Slack-aware once, and writes the selection with all rows.

- [ ] **Step 2:** Run; expect FAIL. **Step 3:** Implement; pooled per-type rate = Σ on-time count / Σ released over the 100 days. **Step 4:** PASS; commit `feat: rule-based checkpoint selection`.

### Task 4: Visible-order rollout planner and its information audit

**Files:** Create `medical_uav/baselines/rollout.py`; Modify `scripts/evaluate.py` (method `rollout`); Test `tests/test_rollout.py`

**Interfaces:**
- Produces: `visible_copy(env) -> MedicalUAVEnv` (deep copy sharing map and config; keeps the cargo and only the pending orders shown in the 12 slots; drops orders not yet released); `rollout_policy(env) -> int` (for each valid action: on a visible copy, take it, then let Slack-aware act until no pending or on-board order is left; score = the copy's total reward, i.e. the v2 compromise; highest score wins; ties go to Slack-aware's own choice).

- [ ] **Step 1: Write the failing tests:** `test_visible_copy_hides_future_and_hidden_orders`; `test_rollout_ignores_future_and_hidden_orders` (on 20 saved mid-day states from screen days: replacing every future order and every pending order outside the slots with different random orders never changes the chosen action); `test_rollout_only_valid_actions` (one low-load day); `test_rollout_at_least_as_good_as_slack_on_its_own_score` (for 10 states the chosen action's score ≥ Slack-aware's action's score).
- [ ] **Step 2:** Run; expect FAIL. **Step 3:** Implement. **Step 4:** PASS; commit `feat(baselines): visible-order rollout planner`.
- [ ] **Step 5:** Measure decision time (median, p95) and evaluate `rollout` with the other baselines on the screen days; record in roadmap §9.
